# ADR-0010: Python Strategy scripts replace the Rule AST

- **Status:** Accepted (2026-11-28). Supersedes [ADR 0005](0005-declarative-strategy-ast.md).
- **Context:** Strategies existed twice: as declarative Rule AST v2 definitions (builder, compiler, tri-state evaluator, setup state machine, AST backtester and live pipeline) and as Python `Strategy` scripts with their own simulator. Two formats meant two evaluators, two backtests and two vocabularies, and the AST pulled indicator-plugin metadata into strategy validation. Every default alert, strategy, indicator and filter is now a class that inherits its abstract base in `joseph_script`; anything else is legacy.
- **Decision:**
  - **One format.** A strategy is a concrete `joseph_script.Strategy` subclass: built-in (`joseph.scripts.builtin.strategies`), an installed plugin (entry-point group `joseph.scripts`) or an immutable tenant script version. The Rule AST, its builder package, rule editor, compiler, evaluator, setup state machine, AST backtester and live pipeline (with its qualification gate) are deleted, with `/v1/strategies*` and `/v1/strategies/{id}/backtests`.
  - **Built-ins.** The former templates become `builtin:ema-trend-long`, `builtin:rsi-reversion-short` and `builtin:pivot-bounce-long`. Each module imports only `joseph_script` and the standard library, declares every parameter (including stop and target risk inputs) as `INPUTS`, plots what it uses and is valid tenant source, so it can be copied and edited.
  - **Orders.** `ctx.entry(side, quantity, stop=None, target=None, comment="")` and `ctx.close(comment="")` queue an order that fills at the next bar's open. Results list every order with its outcome (`pending`, `filled`, `rejected`, `unchanged`), host-reconciled round-trip `trades`, the final `position_size` and `trade_count`/`win_rate_pct` metrics. Backtests are `POST /v1/scripts/{id}/run`.
  - **Stop and target.** Live entries carry them to the execution engine, which places a venue-held stop-loss and take-profit. In simulation the strategy manages exits (reading `ctx.position_stop` / `ctx.position_target`); the built-ins close at the next open after a bar trades through either level.
  - **Activations.** `/v1/strategy-activations` pins a strategy (catalog source hash or tenant version) with inputs to one to twenty instruments, a timeframe, a mode and notification channels; activations are persisted, can be paused, resumed and deleted, and survive restarts. ALERT_ONLY, PAPER and SHADOW can be activated; AUTO_LIVE is refused with 409 `TRADE_MODE_DISABLED` and exists only as an execution-engine deployment with scoped consent.
  - **Signals.** A loop (`JOSEPH_STRATEGY_INTERVAL_S`) re-runs each active activation on closed bars. An order the strategy queued on the newest closed bar becomes a signal: an entry that opens or reverses the position is `ENTRY_CONFIRMED` (direction, planned entry at the bar close, stop, target, reward/risk), a close or the closing half of a reversal is `POSITION_EXITED`. The dedupe key is `strategy|tenant|activation|source_hash|instrument|bar_start|kind|direction`. Each instrument keeps a bar-close checkpoint that starts at activation or resume time, so history is never replayed; a bar that closed more than `max(2 × timeframe, 120 s)` ago is skipped. Signals go through the existing alert routing; PAPER and SHADOW entries are forwarded to the execution engine, ALERT_ONLY entries never.
  - **Version identity.** Deployments bind `strategy_version_id` = `<script_id>:v<version>` for tenant versions and `<catalog id>:v<first 12 hex digits of the source hash>` for built-in and plugin classes. A catalog class whose installed code changed reports an error instead of evaluating; a new activation adopts it. Kill switches match the strategy id before the last `:v`.
  - **Runtime.** Built-in and plugin classes run in process; tenant source needs the isolated Docker runner, otherwise activation is refused and later evaluations record a visible error.
- **Alternatives:** Keep both formats (rejected: duplicated semantics and tests); keep the AST as a code generator for Python (rejected: still two representations to version and validate).
- **Consequences:** Backtest and live share one simulator and one result contract. Saved AST definitions and their activations are not migrated; their signals stay in the history. The execution engine's signal intake, deployments, consent and risk gateway are unchanged. Strategies read OHLCV bars, declared additional series and optional bar fields only; conditions on other market context must come from those inputs.
- **Migration:** Recreate AST strategies as Python `Strategy` scripts (start from a built-in with "Copy to my scripts") and create activations and deployments for their new version ids. `JOSEPH_PIPELINE_ENABLED`, `JOSEPH_PIPELINE_INTERVAL_S` and `JOSEPH_PIPELINE_MAX_INSTRUMENTS` are replaced by `JOSEPH_STRATEGY_ACTIVATIONS_ENABLED` and `JOSEPH_STRATEGY_INTERVAL_S`.
- **Rollback:** Revert the change set; the `strategy_versions` tables of the AST are left untouched in existing databases.
